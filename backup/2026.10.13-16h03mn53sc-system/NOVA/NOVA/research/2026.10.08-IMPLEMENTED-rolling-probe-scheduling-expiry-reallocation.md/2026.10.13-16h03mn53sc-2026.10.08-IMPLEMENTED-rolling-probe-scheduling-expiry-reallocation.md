# 2026-10-08 — Implemented: Rolling Probe Scheduling and Expiry Reallocation

## Status

IMPLEMENTED for the no-new-secret stage.

## Decision

NOVA's six-hour provider health cadence is a **rolling spacing rule**, not a set of immutable wall-clock slots.

A provider check may be advanced when an already-required health probe can consume observed capacity before that capacity expires. This does not authorize NOVA to create work merely to burn a quota, credit, GPU allocation, or other resource.

After the early probe is actually performed, the checked provider is moved to the end of the rolling probe queue. The remaining providers retain the configured six-hour spacing from the actual completed check.

## Example

Normal rolling sequence:

```
A 00:00
B 06:00
C 12:00
D 18:00
```

Suppose NOVA observes that C has capacity expiring at approximately 21:00 while C's next normal check would occur later.

NOVA may select:

```
C 21:00   <- expiry-aware advancement
A 03:00
B 09:00
D 15:00
C 21:00   <- C returns after the other providers
```

The important invariant is not the original clock position of C. It is the **six-hour separation between successive provider checks after the real check completes**.

## Economic interpretation

The scheduler does not automatically translate saved time into money. It records observable scheduling facts such as:

- normal next due time;
- observed capacity deadline;
- time-to-deadline;
- selected reason `EXPIRY_REALLOCATION`;
- provider actually checked;
- resulting rolling queue.

A monetary saving is asserted only when comparable economic evidence exists. Otherwise NOVA can truthfully state that expiring capacity was reused for already-required work without inventing a cash valuation.

## Multiple checked providers

When a heartbeat performs more than one provider probe because of failover, every actually checked provider is moved toward the end of the next rolling cycle in the order in which it was checked. Untouched providers retain their pre-existing queue order.

## Platform scheduling dependency

The scheduling algorithm is implemented independently of the wake-up mechanism.

The repository now contains a lightweight GitHub Actions scheduler tick at five-minute granularity. GitHub documents five minutes as the shortest scheduled-workflow interval and notes that scheduled runs can still be delayed under load. Therefore a provider capacity deadline that requires sub-five-minute precision remains a platform-timing risk rather than something NOVA may assume away.

## Protected constraints

The implementation preserves these constraints:

- stale observations do not become current truth;
- total resources remain distinct from call/rate allowances;
- unknown economics do not receive a positive expiry preference;
- paid capacity requires a comparable non-negative economic case;
- the protected reserve remains enforced;
- expiry alone never creates synthetic work;
- provider checks remain six hours apart in the rolling schedule except where an already-required check is intentionally advanced.

## Remaining external verification

Live confirmation of provider-specific credit/expiry behavior still requires the provider credentials and observed provider measurements. The scheduler can consume those observations once configured; it does not require architecture changes to do so.
