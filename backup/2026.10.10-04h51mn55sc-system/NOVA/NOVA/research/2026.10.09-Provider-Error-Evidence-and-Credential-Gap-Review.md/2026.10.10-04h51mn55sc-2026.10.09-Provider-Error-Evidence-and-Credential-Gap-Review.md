**Observation date:** 2026-10-09  
**Status:** PR #57 OPEN — current branch-head CI passed all 56 offline tests; live-provider outcomes remain pending  
**Run examined:** https://github.com/ACROWN-System/NOVA/actions/runs/37926549165

## Executive finding

The Mistral HTTP 429 / `rate_limited` / code `1300` is not unique to NOVA. Public developer reports contain the same error body and demonstrate that the response can carry Mistral-specific request-rate headers and correlation IDs. The evidence contradicts the assumption that there is no public trail to investigate.

The exact cause for NOVA remains **UNKNOWN** until the actual response headers and current account/model limits are correlated. Public reports show different header values; they must not be treated as measurements of NOVA's account.

## Mistral public evidence

1. Cline issue [#9085](https://github.com/cline/cline/issues/9085), opened 2026-02-04, records HTTP 429, `rate_limited`, and code `1300` on a Mistral API request.
2. gptel issue [#1533](https://github.com/karthink/gptel/issues/1533), opened 2026-09-04, records the same body plus:
   - `mistral-correlation-id`
   - `x-kong-request-id`
   - `x-ratelimit-limit-req-minute`
   - `x-ratelimit-remaining-req-minute`
   That specific report shows both request-rate values as `0`. It also reports that browser-based Mistral Vibe was still usable; that does not establish the state of Platform API entitlements.
3. A separate published error log at [openresource/error.txt](https://github.com/gauravxdev/openresource/blob/main/error.txt) shows the same code 1300 with `x-ratelimit-limit-req-minute: 4` and `x-ratelimit-remaining-req-minute: 0`. That is consistent with an exhausted request window in that different context.
4. The Mistral TypeScript SDK issue [#169](https://github.com/mistralai/client-ts/issues/169) documents successful-response headers including `x-ratelimit-limit-tokens-minute`, `x-ratelimit-remaining-tokens-minute`, `x-ratelimit-limit-req-minute`, `x-ratelimit-remaining-req-minute`, and `x-ratelimit-tokens-query-cost`.
5. The public [OpenCode model smoke review](https://github.com/0xf1d0/opencode-agent-benchmark/blob/95147df5c36e1ce2a5a3c431fefc3bddcbadafa0/docs/mistral-review.md) reports HTTP 200 / `ACCESS_OK` for Codestral while Small and Medium models returned code 1300 in the same set of observations. Its author leaves those models catalog-qualified and marks the rate-limit cause UNKNOWN. This is evidence that model-specific entitlement or limit differences deserve checking; it does not prove a fix for NOVA.
6. The [Cline issue #9085](https://github.com/cline/cline/issues/9085) contains a user report that the same Mistral key worked in another agent, and another commenter said reducing context size per API call worked around their symptoms. That makes payload/context consumption a plausible testable hypothesis when an actual nonzero limit is reported, not a universal code-1300 resolution. It cannot explain a confirmed `x-ratelimit-limit-req-minute: 0` by itself.
7. A detailed [Mistral OCR API evaluation](https://github.com/renchris/claude-infrastructure/blob/2cf75869d56b54517b0ea63a7acf31825d958a16/docs/research/opus55-utilization-2026-09-22/mistral-ocr-eval.md) saw the same response with request limit and remaining both zero. Its `GET /v1/models` succeeded, but the OCR API call was blocked. The report hypothesizes a workspace tier/credit setting and does not claim a verified platform-side fix. OCR is a different endpoint; use this as evidence about the failure family, not proof of NOVA's model-specific cause.

These examples show why code `1300` alone cannot reveal which limit triggered the user's response. A reported limit of zero, an exhausted nonzero limit, monthly token allocation, organization-level enforcement, and other provider conditions must remain distinct until observed. Mistral's own guidance describes RPS, TPM, monthly token limits and organization-level sharing: https://help.mistral.ai/en/articles/698531-why-am-i-hitting-api-rate-limits-and-how-do-i-increase-them

## Implementation gaps found

- The router's allowlist previously omitted Mistral-specific `x-ratelimit-*-req-minute`, `x-ratelimit-*-tokens-minute`, monthly-token names, `mistral-correlation-id`, and `x-kong-request-id`. Therefore, an empty `diagnostic_headers` dictionary was not sufficient to prove that Mistral returned no diagnostic headers.
- Captured `response_headers` were not passed into durable health observations. This lost provider correlation IDs and the raw allowlisted window evidence from structured state.
- The capacity parser recognized Groq's generic header family, but not Mistral's separately named request/token windows.
- The GPU heartbeat workflow previously exported no provider credential environment variables. This branch now maps the candidate `NOSANA_GPU_API_KEY_01` and `HF_ZEROGPU_TOKEN_01` secrets into that workflow without placing secret values in source. The GPU roster's active `providers` list remains empty, so this does not activate a GPU adapter or trigger a provider call.
- Groq's two configured GPT-OSS models returned strict JSON-schema validation failures with an empty generated body. Official Groq docs list both models as supporting strict structured outputs and document GPT-OSS reasoning controls / `max_completion_tokens`. The request was updated on this branch to use a bounded `max_completion_tokens` allowance and low reasoning effort. This is a **testable candidate correction, not yet a live-verified fix**. Sources: https://console.groq.com/docs/structured-outputs ; https://console.groq.com/docs/reasoning

## Wider ecosystem sweep — discovery leads, not endorsements

A fresh pass through current official gateway docs and broader provider directories found additional no-cost access routes. These expand the search space, but not all are proven independent providers and no candidate should be activated from a directory listing alone.

- **Requesty Gateway** — official pricing lists a free plan with free models, 200 requests/day and no card: https://www.requesty.ai/pricing. It routes across upstream providers; treat it as a gateway/aggregator, not as another fully independent model host.
- **Kilo AI Gateway** — official docs allow anonymous access for free models and document 200 requests/hour/IP: https://kilo.ai/docs/gateway/authentication and https://kilo.ai/docs/gateway/models-and-providers. Free routing may include upstream endpoints with their own trial and data-use terms; do not use it with confidential prompts until the selected route and policy are checked.
- **NVIDIA NIM / API Catalog** — official NVIDIA material advertises NIM/API Catalog access at no charge under applicable license terms and free Developer Program access. Exact hosted endpoint quota, payment-method requirement, request caps, data retention and continuing entitlement for NOVA are still **UNKNOWN**. Verify against https://docs.nvidia.com/nim/ and https://build.nvidia.com/.
- **Nous Portal**, **OVHcloud AI Endpoints**, and **Aion Labs** surfaced in third-party discovery catalogs. They remain **UNKNOWN / INVESTIGATE** because current authoritative account/API quotas, no-card requirements, model APIs, commercial terms and privacy conditions were not fully verified in this pass.
- **OpenCode Zen / Console**: do not infer a general free API from a promotion listing. Its current official console documentation describes pay-as-you-go models requiring billing details and credits: https://opencode.ai/v2/docs/console/models/.
- **Discovery indexes**: FreeInference.dev currently indexes a large catalog of models and provider/gateway routes (reported at more than 100 model entries and dozens of providers). Community directories such as https://github.com/pacocartones/free-llm-api-hub are useful for candidate generation, but not proof of provider terms, uptime, privacy, or commercial rights.
