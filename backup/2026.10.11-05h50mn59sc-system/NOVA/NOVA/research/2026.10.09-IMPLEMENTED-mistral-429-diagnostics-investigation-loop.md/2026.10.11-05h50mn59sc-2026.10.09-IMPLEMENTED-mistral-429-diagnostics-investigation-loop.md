# Mistral HTTP 429 diagnostics and investigation loop

**Status:** IMPLEMENTED IN BRANCH; validation pending
**Date:** 2026-10-09
**Scope:** Improve NOVA's provider-neutral HTTP error diagnostics and make the Mistral incident investigation evidence-led. This note does not claim that the underlying Mistral rate-limit cause is already known.

## Evidence ledger

### Verified facts

1. GitHub Actions run [37889314591](https://github.com/ACROWN-System/NOVA/actions/runs/37889314591) completed the heartbeat workflow successfully.
2. That run did execute Mistral as the scheduled probe, using the model alias `mistral-small-latest` and credential environment-variable name `MISTRAL_API_KEY_01`.
3. Mistral returned HTTP `429`, error type `rate_limited`, code `1300`, and message `rate limit exceeded`.
4. The workflow's success means the heartbeat process completed; it does not mean every provider passed.
5. The Mistral Playground test succeeded at a different point in time. This demonstrates that at least one request succeeded, not that the key has unlimited or uninterrupted capacity.
6. The current code already extracts some rate-limit headers into capacity observations, but the HTTP-error log did not expose those observations and the error body was lowercased before recording. This change preserves the original error text and records an allowlisted set of diagnostic response headers.

### Unknown — do not silently convert to false or infer

- Which limit triggered the 429: requests per second, tokens per minute, monthly token allowance, or another provider-side enforcement condition.
- Whether Mistral sends a `Retry-After` header or usable rate-limit headers for this exact response.
- Whether the model alias `mistral-small-latest` resolves to a model with a different limit than the model the user inspected in the dashboard.
- Whether other concurrent activity in the same organization contributed to the limit.
- Whether a transient provider-side condition contributed.
- Whether the earlier UI wording “credit expired” referred to the same failure class as this observed 429. The latest raw API response is evidence of rate limiting, not proof of expired credits.

## Exhaustiveness rule, adapted to provider incidents

Do not stop at the first plausible explanation or at the most visible dashboard value. Examine the distinct causes supported by the response and the provider's actual plan and model rules. Continue until each plausible cause is verified, falsified by evidence, or explicitly classified UNKNOWN/BLOCKED and further investigation has diminishing returns.

Keep these distinctions explicit:

- UNKNOWN is not FALSE.
- Candidate explanation is not a verified cause.
- A rate limit is not the same thing as a total credit balance.
- A model's displayed TPM/RPS is not proof that the current request had remaining allowance.
- A successful Playground request is not proof that every subsequent automation request must succeed.
- Missing response headers mean NOT_EXPOSED, not unlimited capacity.

## Anti-looping execution rule

Use one evidence-producing cycle at a time:

**Need information → Research → Verify → Classify → Continue**

For every cycle, record:
1. The exact question being resolved.
2. The smallest observation or test that can resolve it.
3. The evidence and its source/time.
4. Classification: VERIFIED, REFUTED, UNKNOWN, BLOCKED, or DEFERRED.
5. The next step only if evidence justifies it.

Do not repeat speculative explanations or recommend billing changes before evidence distinguishes them. Avoid multiple uncontrolled retries that can themselves consume request-rate allowance. Do not enable pay-as-you-go, add a payment method, or replace the key merely to test a hypothesis.

## Investigation order

1. **Capture the response safely.** Preserve HTTP status, original response body, model, credential *environment-variable name*, and only allowlisted diagnostic response headers. Never log API keys, authorization headers, or arbitrary headers.
2. **Classify the limit evidence.** If present, use `Retry-After`, rate-limit limit/remaining/reset headers, and provider request ID. If absent, mark those measurements NOT_EXPOSED.
3. **Correlate model and organization scope.** Compare the exact requested/resolved model with the model-specific organization limits; remember organization-level limits can apply across workspaces.
4. **Correlate usage and timing.** Compare the event time with API usage and other activity without assuming that a small displayed cost means no rate limit was reached.
5. **Run one controlled follow-up only if needed.** Respect `Retry-After` when present; otherwise avoid rapid repeat probes. Preserve the prior result and compare new evidence.
6. **Escalate only with a reproducible evidence bundle.** Include timestamp, HTTP status, error code/type/message, model, redacted request ID if present, and observed limits. Never include the secret.

## Implemented in this change

- Preserve original-case HTTP error body while keeping case-insensitive permanent-error classification.
- Capture an allowlist of retry/rate-limit/request-ID response headers in HTTP-error probe observations.
- Include those safe headers in provider error logs.
- Add unit tests for body preservation, header allowlisting, Mistral 429 diagnostics, and capacity extraction.
- Do not change provider rotation, retry policy, billing settings, secret values, or provider health classification rules.
