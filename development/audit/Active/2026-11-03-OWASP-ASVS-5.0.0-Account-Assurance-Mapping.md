# OWASP ASVS 5.0.0 — AstroCrown Account Assurance Mapping

**Snapshot date:** 2026-11-03  
**Scope:** Local passkey-first account prototype, offline recovery, sessions and administrator wallet step-up.  
**Assessment type:** Preliminary engineering evidence map only.  
**Status:** No formal ASVS verification level selected; no independent assessment or certification claimed.

## Purpose and use

This record maps the current AstroCrown account prototype to the relevant ASVS 5.0.0 verification areas so free engineering and test work can be prioritized and preserved.

It is not a requirement-by-requirement conformance statement. No ASVS requirement is marked PASS solely because a related feature or test exists. A final assessment must enumerate each applicable versioned requirement, define the verification method, capture the exact test evidence, record exceptions and limitations, and be independently reviewed before any external assurance claim.

The stable ASVS 5.0.0 release was published on 30 May 2025. Use version-qualified identifiers such as `v5.0.0-...` in any future detailed test matrix so later standard revisions do not silently change what a reference means.

## Preliminary family-level map

| ASVS area | Evidence present in the local prototype | Current limitations / next verification |
|---|---|---|
| **V2 — Validation and Business Logic** | API handlers validate allowed fields, account identifiers, WebAuthn credential structures, challenge references, recovery-key formats, wallet addresses/chain IDs and request sizes. Server-side validation is authoritative; browser form checks are usability only. | Build an exhaustive requirement matrix for every endpoint and state transition. Test malformed, oversized, inconsistent and cross-object input; concurrency and abuse limits; API-level business-rule bypasses. This table does not claim full V2 coverage. |
| **V6 — Authentication** | WebAuthn discoverable registration/sign-in, required user verification, random one-time challenges, RP ID/origin checks, server-side cryptographic verification, email/password login retired in default mode, and one-time offline recovery-key replacement. Experimental ML-DSA algorithms are offered before compatible classical algorithms; the verifier accepts the same allow-list and stores the actual COSE algorithm. | Genuine ML-DSA browser/authenticator interoperability is not established; the WebAuthn mapping remains an Internet-Draft. Multi-passkey enrollment/removal, sensitive-action reauthentication coverage, authenticator lifecycle management and production account recovery procedures remain incomplete. Do not claim an ASVS verification level. |
| **V7 — Session Management** | Random session tokens are issued after verified passkey authentication; the database stores token hashes. Local cookies are HttpOnly and SameSite=Strict. Sessions expire; recovery revokes sessions; administrator wallet step-up is separate and short-lived. Logout and account continuity are covered by API/browser tests. | The prototype uses localhost HTTP and therefore does not establish the production Secure-cookie/HTTPS configuration. Production session storage, cross-instance behavior, full session/device management, inactivity/absolute lifetime policy validation, concurrency, and operational revocation procedures remain unqualified. |
| **V8 — Authorization** | Roles and permissions are server-owned. A new passkey account defaults to `user`. Wallet connection or signature cannot create a role. Administrator actions require separately granted permissions and a registered EVM/SIWE wallet step-up. Appointment/revocation and recipient-scoped communications have API/browser regression coverage. | Production role provisioning, owner identity/bootstrap, independent privileged-action recovery, monitoring, review cadence and protection from privileged infrastructure operators are not established. Expand endpoint-by-endpoint function/data/field authorization tests. |
| **V11 — Cryptography** | The relying-party library verifies WebAuthn signatures and public-key credentials; OS CSPRNG is used for challenges, IDs, sessions and a 256-bit one-time recovery key. Recovery stores a salted one-way verifier rather than the readable key. ML-DSA algorithm parsing and metadata storage have unit/API tests. | The recovery verifier construction and all cryptographic choices need independent review before production. The ML-DSA WebAuthn mapping and COSE identifiers remain experimental/TBD in the cited draft, and tests do not yet prove a real authenticator-generated ML-DSA credential/signature. No end-to-end encryption or post-quantum protection for the whole service is claimed. |
| **V14 — Data Protection** | Private key material is not sent to the server; passkey public keys and credential metadata are stored. Recovery secrets are not retained in readable form. Session tokens are hashed. Administrator communication audit records avoid duplicating private message bodies. | The local SQLite prototype is not an encrypted, shared production database. There is no complete production retention, export, deletion, backup/restore, data classification, database encryption or end-to-end encryption programme. The application/database operator trust boundary remains. |
| **V16 — Security Logging and Error Handling** | Security and administrator audit records track selected account recovery, administrator permission/role, wallet and communication events. Some tests verify audit linkage and ensure private communication content is not duplicated in governance details. | Full successful/failed authentication event coverage, authorization-denial coverage, log integrity/segregation, alerting/monitoring, retention and production incident handling must be mapped and tested. A local audit table is not an immutable external audit service. |

These are focus areas selected for the account scope, not the complete set of ASVS requirements applicable to the wider website or its service dependencies.

## Next $0 verification steps

1. Convert the relevant ASVS 5.0.0 requirements into a version-qualified, requirement-by-requirement matrix; do not mark requirements passed until a test method and evidence artifact exist.
2. Prioritize V6, V7 and V8 because authentication, session handling and authorization are the direct scope of this prototype.
3. Extend tests for challenge replay/substitution, account and user-handle cross-binding, session rotation and termination, concurrent recovery, role escalation, permission delegation and authorization denials.
4. Record production-only requirements as **BLOCKED / NOT TESTABLE LOCALLY**, not as failures or passes. These include HTTPS/Secure cookies, production shared storage, backup/restore, monitoring, incident response and external security contact.
5. Keep ML-DSA as a separate experimental test track. The presence of a server-side algorithm option must not be mistaken for actual client/authenticator conformance.
6. Have an independent reviewer validate the final matrix before making any public statement about ASVS verification.

No ASVS Level 1, Level 2 or Level 3 claim is made by this preliminary mapping. No OWASP endorsement or certification exists for this project.
