## 1. Purpose and boundaries

This record maps selected OWASP Application Security Verification Standard (ASVS) 5.0.0 controls to the current account prototype. It is intended to guide $0 engineering and test work, identify what the repository evidence does and does not establish, and prevent old test snapshots or prototype-only controls from being described as production assurance.

The scope is the account subsystem in this development branch. It is not an assessment of the entire AstroCrown website, exchange, blockchain, wallet custody, infrastructure, public deployment, NOVA, or third-party services.

This is **not** a requirement-by-requirement ASVS verification. A related feature or a passing test does not by itself establish that an ASVS requirement is met. The mapping does not select Level 1, Level 2, or Level 3; in particular, local user-verification settings must not be treated as automatic proof of an ASVS MFA or hardware-attestation requirement.

Use version-qualified references such as `v5.0.0-6.3.1`. OWASP identifies ASVS 5.0.0 as the stable release published on 30 May 2025. The changing development/bleeding-edge content is not used as the baseline for this record.

## 2. Status vocabulary

| Status | Meaning |
|---|---|
| **Local evidence present** | The named behavior is visible in the prototype and/or has a corresponding local test. This is not an ASVS pass. |
| **Partial** | A control or related behavior exists, but its full requirement, policy, coverage, or operating boundary is not demonstrated. |
| **Not demonstrated** | The current source and test evidence do not establish the requirement. |
| **Not implemented** | The relevant UI, process, control, or test is absent from the reviewed prototype. |
| **Not directly applicable** | The specific ASVS clause addresses a different mechanism; related design controls are not being substituted for it. |
| **Production blocked** | Local loopback evidence cannot verify the hosted, HTTPS, deployment, operational, or independent-assessment requirement. |

Statuses are evidence labels for this snapshot, not audit conclusions. Any future detailed matrix must record the exact versioned requirement, test method, expected and actual result, artifact, limitation, finding owner, remediation and retest.

### Authentication-specific caveats

- Required WebAuthn user verification is not, by itself, proof of an ASVS Level 2 MFA design or Level 3 attested hardware authenticator.
- The default ordinary sign-in path does not request an email, password, SMS factor, wallet, balance or blockchain transaction.
- Existing EVM/SIWE proof is a separate administrator privilege step-up; it does not silently become ordinary account sign-in.
- The server advertises experimental ML-DSA algorithms ahead of classical fallbacks and records the COSE algorithm encoded in a registered public key. A new test generates ephemeral ML-DSA-44/65/87 keypairs, constructs synthetic WebAuthn assertions and verifies genuine signatures through the server's authentication path; wrong challenges and altered signatures are rejected. This qualifies backend cryptographic verification only—not browser, CTAP or physical-authenticator interoperability.
- The ML-DSA WebAuthn mapping and COSE values used by the prototype remain experimental; do not claim FIDO/WebAuthn profile standardization or real-device compatibility.

| `v5.0.0-7.1.1` | ASVS asks for documented inactivity and absolute session lifetimes, including rationale. The prototype has a 30-minute absolute session expiry. | **Partial.** No inactivity timeout is implemented or documented; produce a risk-based policy for both timeout types. |
| `v5.0.0-7.1.2` | The concurrent-session policy and maximum behavior should be documented. The dashboard exposes an active-session count. | **Not demonstrated.** Define permitted concurrency, limits, user choice, and behavior at the limit. An active count is not a session-management feature. |

| `v5.0.0-7.2.4` | A new session token is generated after authentication. | `v5.0.0-7.4.1` | Logout and expiry must invalidate stateful session data. | `v5.0.0-7.4.2` | All active sessions must terminate when an account is disabled or deleted. | **Not demonstrated.** Add explicit disable/delete semantics and tests or document why the operation does not exist. |
| `v5.0.0-7.4.3` | Users should be offered termination of other sessions after authentication-factor changes. | `v5.0.0-7.4.4` | Authenticated pages should have visible logout access. The account UI exposes logout. | **Partial.** Verify consistency and accessibility across every authenticated route, including communications and administrator views. |
| `v5.0.0-7.4.5` | Administrators should be able to terminate sessions for one or all users. | **Not implemented / not demonstrated.** No production-safe administrative session termination operation is established. |
| `v5.0.0-7.5.1` | Sensitive account attributes affecting authentication/recovery should require full re-authentication. | **Not demonstrated.** Map every future credential, recovery, identity and account-security mutation to a step-up requirement. |
| `v5.0.0-7.5.2` | Users should be able to view and terminate active sessions after re-authentication. The dashboard currently displays a count. | **Not implemented.** No complete per-session listing, metadata view or re-authenticated termination UI is evidenced. |
| `v5.0.0-7.5.3` | Highly sensitive operations require further authentication. The administrator dashboard/actions use a separate short-lived wallet step-up. | **Partial and scope-specific.** Map all sensitive operations, ensure step-up binding/expiry/replay protections and test each action. This does not establish a general application-wide re-authentication policy. |

## 5. Boundary families — not a full assessment

| ASVS family | Observed prototype evidence | Gap / boundary |
|---|---|---|
| **V2 — Validation and Business Logic** | Server-side validation exists for API shapes, account identifiers, WebAuthn challenge references, recovery values, wallet addresses/chain IDs and bounded request bodies. | No exhaustive endpoint/state-transition matrix, full cross-object authorization review, abuse-race suite or business-logic assessment is claimed. |
| **V4 — API and Web Service** | Responses set explicit Content-Type and security headers; JSON POST handling checks Origin, Content-Type, body size and object shape; unsupported cross-origin OPTIONS requests are rejected. | This is not a V4 pass. Method coverage, request parsing/smuggling, intermediary trust, production proxy behavior and all API responses require dedicated tests. |
| **V8 — Authorization** | Roles and permissions are server-owned; new users default to `user`; admin functions require separately granted permissions and wallet step-up; recipient-scoped communications are tested. | Full object/function/field authorization matrix, production provisioning, delegated authority, privileged operator controls and every endpoint remain to be reviewed. |
| **V11 — Cryptography** | OS CSPRNG is used for challenges, session tokens, account identifiers and recovery material; WebAuthn signatures are verified through the pinned library. | Independent cryptographic design review, recovery verifier review, key-management/rotation, dependency review and production key protection remain outstanding. No whole-service post-quantum claim is made. |
| **V12 — Secure Communication** | The local development server binds to loopback and allows HTTP only for localhost WebAuthn development. | The cookie intentionally lacks the Secure attribute in this HTTP-only prototype. Production HTTPS, Secure cookies, TLS configuration, HSTS and deployment-edge behavior are **production blocked** and must be verified before real credentials are accepted. |
| **V13 — Configuration** | Several response security headers and conservative local-server boundaries are present. | No complete configuration baseline, production hardening review, secrets/runtime configuration audit or deployment verification is claimed. |
| **V14 — Data Protection** | Passkey private keys remain with authenticators; recovery keys and session tokens are not stored in readable form; JSON responses use no-store; administrator communication audit records avoid duplicating private message bodies. | Local SQLite is not a production encrypted/shared datastore. Retention, backup/restore, export/deletion, access governance, data classification and end-to-end encryption are not qualified. The backend/database operator trust boundary remains. |
| **V16 — Security Logging and Error Handling** | Selected recovery, administrator role/permission, wallet and communication events are audited; tests check selected audit linkage and private-message minimization. | Successful/failed authentication coverage, access-denial events, integrity, segregation, alerting, retention, monitoring and production incident response require a detailed review. A local audit table is not an immutable external audit service. |

The account implementation has a Content-Security-Policy that currently permits inline scripts and styles for the local prototype. This must be reconsidered during production hardening; it is not treated as an ASVS control satisfied by the presence of a CSP header.
