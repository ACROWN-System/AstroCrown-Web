AstroCrown · Account access

Security assurance

This page explains the current evidence and limitations of the development-only account prototype. It is separate from the Terms of Use and Privacy Policy.

Status: Development prototype only.

The prototype is not production authentication, has not received an independent security audit or certification, and must not be used with real credentials, personal email accounts, crypto wallets or valuable assets.

Controls present in the local prototype

  • Password verifiers use PBKDF2-HMAC-SHA256 with a random salt and 600,000 iterations; raw passwords are not stored.
  • Session tokens are generated randomly; the SQLite session store keeps a token hash.
  • The test server binds to loopback and checks the expected localhost Host/Origin.
  • Request bodies are bounded; account and sign-in attempts have in-process rate limits.
  • Local cookies are HttpOnly and SameSite=Strict. This HTTP-only localhost setting is not a production cookie configuration.
  • Basic response headers, a Content Security Policy, and no-store responses are set by the local server.
  • The hosted browser preview uses a disposable in-memory demonstration and makes no account API request.

Not implemented

  • Email ownership verification, email delivery and password-reset delivery.
  • Production HTTPS hosting, production session/CSRF configuration, persistent production storage and backup/restore.
  • Development-only administrator controls now include a local owner-operated provisioning CLI, a registry for up to three wallets, server-issued SIWE challenge/signature verification, a ten-minute wallet step-up on the existing account session, and a read-only gated admin console. Ordinary registration cannot assign a role and role assignment alone never authorizes admin access. There is no public provisioning endpoint and no production role administration, wallet enrollment interface, privileged admin operations, or all-wallet-loss recovery.
  • Imperial HSIAN recovery for loss of every administrator wallet.
  • Real passkeys, recovery-code flows, connected-wallet registration or user session management.
  • Production profile/avatar synchronization or image uploads. Six built-in avatar glyphs can be selected in the local account prototype only; no external image is uploaded or fetched.
  • Newsletter delivery, a verified referral/reward system, approved production Terms/Privacy, or user account deletion/export.
  • Independent penetration testing, external certification, production incident response and a complete ASVS verification.

What the tests mean

Automated tests can demonstrate the specific local prototype behaviors that they exercise, such as password verification, request validation, session invalidation and the browser demo journey. A passing test suite does not establish that every security control is present or that future production deployment is secure.

The account UI and wallet-signature lab are separate development components. Connecting a wallet is not ordinary account login and must not create administrator privileges.

References used for design

  • NIST SP 800-63B-4 — authenticator and password guidance.
  • OWASP ASVS 5.0.0 — application security verification requirements.
  • OWASP Password Storage Cheat Sheet.
  • OWASP Session Management Cheat Sheet.
