AstroCrown · Account access

Why wallet sign-in?

AstroCrown uses one primary identity wallet to establish account ownership. This page explains what the wallet proves, what AstroCrown can and cannot see, how recovery works, and which wallet types are currently supported. It is separate from the Terms of Use and Privacy Policy.

Why use a primary identity wallet?

Your wallet is your account identity. AstroCrown asks the wallet to sign a fresh, short-lived message that is bound to this exact website origin, wallet address, network and one-time challenge. The server verifies that signature before creating a session or a new account.

  • No email address, phone number, password, SMS code or third-party identity provider is required for this sign-in method.
  • AstroCrown receives the public wallet address and network identifier. The wallet's private key and seed/recovery words remain under your control and are never sent to AstroCrown.
  • The sign-in message is signed off-chain. It is not broadcast to a blockchain, does not cost gas, does not move assets and does not grant token approvals or spending permission.
  • The server creates a random, short-lived challenge and accepts it only once. It checks the exact message and recovers the signing EVM address before issuing an ordinary account session.
  • The primary identity wallet is distinct from any auxiliary wallet you may connect later for a specific transaction. Connecting a transaction wallet does not make it another account identity.

Privacy is pseudonymous, not anonymous. You do not need to provide an email or phone number for this authentication, but the public wallet address is visible to AstroCrown and may be linked by anyone to public blockchain activity associated with that address. Choose a wallet with an appropriate privacy posture.

Primary wallet sign-in: current implementation boundary

  • The browser obtains the selected public address and chain ID from an injected EVM wallet provider. The server then issues a random, origin-bound, expiring challenge.
  • The wallet signs the exact challenge using EIP-191 personal-sign. The server verifies the signer address, one-time challenge, expiry and exact message before it creates a new session.
  • One primary wallet address can be associated with only one AstroCrown account. A different address cannot sign in to that account merely because a user knows its account identifier.
  • The database stores the public address, chain identifier, account linkage, timestamps and session hashes. It does not store a wallet private key, mnemonic, seed phrase or wallet recovery secret.
  • Initial scope is EVM externally owned accounts (EOAs). Smart-contract wallets requiring EIP-1271 validation and non-EVM wallets on Solana, TRON or Bitcoin are not yet qualified by this implementation.
  • Older passkey-created staging accounts remain available through a clearly labelled legacy access path. This does not make passkeys the primary identity method for new wallet accounts.

Legacy passkey controls retained for older test accounts

  • WebAuthn passkey registration uses discoverable credentials (resident keys), required user verification and attestation preference "none".
  • Discoverable passkey sign-in does not require an email address, password or account identifier to be submitted to the login endpoint.
  • The maintained WebAuthn relying-party library validates client data, challenge, RP ID hash, origin, user presence, user verification and the authenticator signature. The application stores the credential ID, public key, signature counter and lifecycle metadata; no passkey private key is sent to or stored by AstroCrown.
  • Registration and authentication challenges are generated randomly, bound to one ceremony, stored server-side, expire and are atomically marked used. Replay and stale concurrent credential updates are rejected.
  • Account IDs are independent of email and wallet addresses. New passkey accounts use a local random account identifier and default to the ordinary user role; a passkey cannot grant administrator authority.
  • Initial registration generates a 256-bit random one-time recovery key. The readable key is returned once; the database stores a 16-byte salt and 32-byte SHA-256 verifier only. The key is not written to application logs or the audit detail.
  • Recovery verifies the account identifier and unused recovery key, requires a new WebAuthn registration ceremony, consumes the old key, disables all previously registered passkeys, revokes all existing sessions, issues a replacement key and records a security audit event.
  • Recovery attempts and account-creation/sign-in attempts use persistent SQLite-backed rate limits. Invalid/expired/reused challenges and failed recovery proofs are rejected.
  • Session tokens are random; SQLite stores their hashes. Local cookies are HttpOnly and SameSite=Strict. These HTTP localhost cookie settings are not a production HTTPS configuration.
  • The server binds only to loopback and checks the canonical localhost Host/Origin. Request bodies are bounded. Responses are no-store and use basic security headers and a Content Security Policy.
  • Account registration/sign-in/recovery does not invoke an email or SMS provider, a paid identity provider, a third-party authentication API or a blockchain transaction.
  • The server offers experimental ML-DSA-65, ML-DSA-44 and ML-DSA-87 registration algorithms before classical fallbacks. It passes the same allow-list to its registration verifier and records the algorithm actually encoded in each new credential.
  • The User dashboard counts only active credentials whose stored algorithm is recorded as ML-DSA. An advertised option or a classical fallback is not counted as a post-quantum passkey.
  • Administrator role/permission checks and the EVM/SIWE administrator step-up remain separate from ordinary passkey authentication. Role appointment and revocation target an existing member by the public AC- account identifier shown in the User dashboard; the identifier is not an authenticator. Email is not required. Wallet connection alone never creates a user account or administrator role.

Not implemented or not production-qualified

  • Production HTTPS hosting, RP ID/origin configuration for the public site, durable shared database, secret management, backup/restore, deployment monitoring and operational incident response.
  • User-facing enrollment/revocation of multiple passkeys, device/session management and passkey-confirmed reauthentication for every sensitive action.
  • Additional wallet families and smart-contract wallet verification. The current primary identity adapter supports EVM externally owned accounts using EIP-191 personal-sign; EIP-1271, Solana, TRON and Bitcoin primary-wallet authentication are not yet implemented or qualified.
  • Recovery after the primary wallet and every backup/recovery route controlled by the user's wallet provider have been lost. AstroCrown does not possess the wallet's secret material and provides no staff, administrator, email or SMS override; the associated account may be permanently unrecoverable.
  • Client-side/end-to-end encryption that prevents application/database operators from reading plaintext account data. WebAuthn authentication alone does not provide this data-confidentiality property.
  • Production owner/admin governance, production role management, external security operations, all-admin-wallet-loss Imperial HSIAN recovery, and production account support.
  • Independent penetration testing, independent security review, formal ASVS verification, external certification, approved production Terms/Privacy, and production privacy/data retention/export/deletion procedures.
  • Synced passkeys may use the user's platform credential-sync provider. Device-bound credentials or a compatible FIDO2 hardware key are alternatives where supported; hardware key purchase is not required by this local prototype.
  • The ML-DSA WebAuthn/CTAP mapping is an active IETF Internet-Draft. Its requested COSE identifiers are marked TBD in that draft. This local profile is experimental; cross-browser, platform-authenticator, credential-sync, roaming-key and FIDO-certified interoperability have not been demonstrated. Classical fallback remains enabled.
  • Auxiliary transaction-wallet connections, multi-chain primary-identity adapters and Astro-Wallet integration remain separate future work. Auxiliary wallets will not become alternate account identities or recovery keys.

What the automated tests mean

The local Python suite exercises WebAuthn option generation, RP/origin requirements, registration and authentication challenge handling, replay rejection, credential persistence, user-handle matching, recovery-key storage and rotation, one-time consumption, passkey replacement, session revocation, and ordinary/admin separation. Some server endpoint tests deliberately mock the cryptographic library verdict so they can isolate database and lifecycle behavior; they do not simulate forged real-world signatures as accepted proofs.
