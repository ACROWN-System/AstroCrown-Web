AstroCrown · Account access

Security assurance

This page describes the current local passkey-first account prototype, the specific tests that exercise it, and the controls that remain absent. It is separate from the Terms of Use and Privacy Policy.

Status: Development prototype only — local passkey/recovery development test.

WebAuthn passkey registration/sign-in and one-time offline recovery are implemented for loopback testing. This is not production authentication, an independent security audit, a certification or a guarantee of account recovery. Do not use real credentials, personal recovery material, real wallets or valuable assets.

Controls present in the local prototype

  • WebAuthn passkey registration uses discoverable credentials (resident keys), required user verification and attestation preference "none".
  • Discoverable passkey sign-in does not require an email address, password or account identifier to be submitted to the login endpoint.
  • The maintained WebAuthn relying-party library validates client data, challenge, RP ID hash, origin, user presence, user verification and the authenticator signature. The application stores the credential ID, public key, signature counter and lifecycle metadata; no passkey private key is sent to or stored by AstroCrown.
  • Registration and authentication challenges are generated randomly, bound to one ceremony, stored server-side, expire and are atomically marked used. Replay and stale concurrent credential updates are rejected.
  • Account IDs are independent of email and wallet addresses. New passkey accounts use a local random account identifier and default to the ordinary user role; a passkey cannot grant administrator authority.
  • Initial registration generates a 256-bit random one-time recovery key. The readable key is returned once; the database stores a 16-byte salt and 32-byte SHA-256 verifier only. The key is not written to application logs or the audit detail.
  • Recovery verifies the account identifier and unused recovery key, requires a new WebAuthn registration ceremony, consumes the old key, disables all previously registered passkeys, revokes all existing sessions, issues a replacement key and records a security audit event.
  • Recovery attempts and account-creation/sign-in attempts use persistent SQLite-backed rate limits. Invalid/expired/reused challenges and failed recovery proofs are rejected.
  • Session tokens are random; SQLite stores their hashes. Local cookies are HttpOnly and SameSite=Strict. These HTTP localhost cookie settings are not a production HTTPS configuration.
  • The server binds only to loopback and checks the canonical localhost Host/Origin. Request bodies are bounded. Responses are no-store and use basic security headers and a Content Security Policy.
  • Account registration/sign-in/recovery does not invoke an email or SMS provider, a paid identity provider, a third-party authentication API or a blockchain transaction.
  • Administrator role/permission checks and the EVM/SIWE administrator step-up remain separate from ordinary passkey authentication. Wallet connection alone never creates a user account or administrator role.

Not implemented or not production-qualified

  • Production HTTPS hosting, RP ID/origin configuration for the public site, durable shared database, secret management, backup/restore, deployment monitoring and operational incident response.
  • User-facing enrollment/revocation of multiple passkeys, device/session management and passkey-confirmed reauthentication for every sensitive action.
  • The optional wallet authenticator as a backup for ordinary account recovery. The currently implemented EVM/SIWE wallet path is limited to administrator wallet enrollment and administrator step-up. Bitcoin, Solana and contract-wallet authenticators are not supported here.
  • Recovery after all passkeys and the offline recovery key are lost. No staff, administrator, email or SMS override is provided; the account may be permanently unrecoverable.
  • Client-side/end-to-end encryption that prevents application/database operators from reading plaintext account data. WebAuthn authentication alone does not provide this data-confidentiality property.
  • Production owner/admin governance, production role management, external security operations, all-admin-wallet-loss Imperial HSIAN recovery, and production account support.
  • Independent penetration testing, independent security review, formal ASVS verification, external certification, approved production Terms/Privacy, and production privacy/data retention/export/deletion procedures.
  • Synced passkeys may use the user's platform credential-sync provider. Device-bound credentials or a compatible FIDO2 hardware key are alternatives where supported; hardware key purchase is not required by this local prototype.
  • Ordinary account-level wallet-backup enrollment, multi-chain wallet credential schema and Astro-Wallet integration remain separate future work.

What the automated tests mean

The local Python suite exercises WebAuthn option generation, RP/origin requirements, registration and authentication challenge handling, replay rejection, credential persistence, user-handle matching, recovery-key storage and rotation, one-time consumption, passkey replacement, session revocation, and ordinary/admin separation. Some server endpoint tests deliberately mock the cryptographic library verdict so they can isolate database and lifecycle behavior; they do not simulate forged real-world signatures as accepted proofs.

The headless Chrome test uses a browser virtual authenticator to exercise real WebAuthn registration, discoverable sign-in and the recovery/replacement ceremony in the local environment. A virtual-authenticator CI pass is evidence for that tested browser path, not proof of universal device/browser compatibility.

Standards and design references

  • W3C WebAuthn Level 3 — public-key browser authentication API.
  • OWASP Passkey Security Cheat Sheet — relying-party implementation, origins, credential lifecycle and recovery.
  • NIST SP 800-63B-4 — authenticator management and recovery guidance. AstroCrown's 128-bit minimum recovery-key target is a project-selected margin; NIST's saved recovery-code minimum is 64 bits.
  • OWASP ASVS 5.0.0 — broader application security verification baseline.

These are engineering references. Their use is not certification, automatic conformance or independent security review.
